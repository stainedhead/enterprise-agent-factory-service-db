# Architectural decision record

Decisions local to this repository. Cross-repo decisions live in the root repository.

## ADR-001 Plain SQL migrations with an embedded Go runner

- Status: Accepted
- Context: the schema must be reviewable as SQL, reproducible, and applied by the API at startup.
- Decision: numbered `.up.sql`/`.down.sql` files embedded with `go:embed`; a small runner with an advisory
  lock and checksum guard instead of a third-party migration framework.
- Consequences: one migration path for CI, local and production; no ORM-generated DDL.

## ADR-002 Application-generated prefixed ULIDs

- Status: Accepted
- Context: ids appear in CLI output, logs and URLs; they should be sortable and self-describing.
- Decision: `text` ids like `team_01JD…`, generated by the API, checked by `afs.ulid_ok`.
- Consequences: no database sequences for entity ids; ids are safe to show to users.

## ADR-003 Row-level security as defense in depth

- Status: Accepted
- Context: authorization is enforced in the API; a missed `WHERE team_id = …` must not leak data.
- Decision: RLS on team-owned tables for `afs_app`, driven by per-transaction settings.
- Consequences: every query from afs-api must run inside a transaction that sets the scope.

## ADR-004 Text + CHECK instead of enum types

- Status: Accepted
- Decision: enumerated values are `text` with `CHECK` constraints so they can change in a normal migration.

## ADR-005 A lock timeout on every migration transaction

- Status: Accepted (000015 release)
- Context: a DDL statement that waits for a lock held by a long transaction makes every later query on
  that table queue behind it, so a migration on rollout can stall the API. The PRD's observability NFR
  asked for a `lock_timeout`.
- Decision: `migrate.Up` and `migrate.Down` set `lock_timeout` locally in each migration transaction,
  10 s by default, changeable with `WithLockTimeout` (0 disables it) and `afs-migrate --lock-timeout`.
  It is not set on the advisory-lock wait, which must keep queueing concurrent migrators.
- Consequences: a blocked migration fails with `55P03` and can be retried; `Up`/`Down` take variadic
  options, so existing callers compile unchanged.

## ADR-006 Prove rules from the catalog, not from a hand-kept list

- Status: Accepted (000015 release)
- Context: per-table isolation and change-feed tests drift as tables are added.
- Decision: tests that state a rule for "every table" select the tables from the system catalog and run one
  subtest each against a shared fixture with rows for other teams in every team table.
- Consequences: a new team table, or a new revision table, fails CI until it is covered by RLS, a notify
  trigger and fixture rows.

## ADR-007 Derived values are set by trigger, not trusted from the writer

- Status: Accepted (000015 release)
- Context: `cost_reconciliations.status` and `api_keys.created_at` were written by callers, so a rule that
  depended on them (variance alerting, the 90-day key expiry) could be wrong or bypassed.
- Decision: a `BEFORE` trigger computes `status` from the row and `billing.variance_alert_pct`; another
  sets `api_keys.created_at = now()` on insert and refuses a change.
- Consequences: writers may omit these values; rows written before 000015 keep theirs.

## ADR-008 Pre-scope lookups and reconciler writes go through named SECURITY DEFINER functions

- Status: Accepted (000016 release)
- Context: `afs-api` must find an API key or a workload before it knows the caller's team, list the team
  directory for security operators who see no team, and the reconciler must create remediation teams
  although it may not write desired state chosen by people (`-restapi` X-DB-1 to X-DB-4).
- Decision: one `SECURITY DEFINER` function per path (`authenticate_api_key`, `resolve_workload`,
  `team_directory`, `instantiate_work_order_team`), each with a pinned `search_path`, no PUBLIC execute and
  EXECUTE for the one or two roles that need it, returning only the columns the caller needs. Policies stay
  team-scoped; the only new policies are INSERT-only (own audit rows, security operator work order events).
- Consequences: no service admin session is needed for a lookup, and no role gains read access to other
  teams' rows. Each function is a reviewed entry point with catalog-checked grants
  (`executableBy` in `migrate/service_access_test.go`); a new pre-scope need is a new function, not a
  wider policy.

## ADR-009 A login-less edge role that reaches data only through functions
- Status: Accepted (000020 release)
- Context: the Paperclip collaboration edge is the one AFS component reachable from outside the cluster
  network. If it is compromised, the database must give it as little as possible (-db PRD DB-41 to DB-52,
  root database contract section 7.2).
- Decision: a new group role `afs_edge` with no privilege on any table, view or sequence. It gets `USAGE` on
  schema `afs` and `EXECUTE` on ten `SECURITY DEFINER` functions (routes, settings, principal lookups,
  access counts, the secret-detected event, sessions and one-time handoffs) that return named columns only.
  Session ids and handoff codes are stored as SHA-256 hashes in tables no role can read. The default `PUBLIC`
  execute privilege on the older `SECURITY DEFINER` partition helpers is revoked so the role cannot reach them.
- Consequences: a test lists every relation and function and fails if `afs_edge` gains anything outside its
  list (`TestEdgeRole`). The role is created by `bootstrap/roles.sql`, which a DBA runs first (migration
  000020 refuses to run without it, `55000`), because `afs_owner` cannot create cluster roles.

## ADR-010 Guards that key on the caller are SECURITY INVOKER
- Status: Accepted (000020 release)
- Context: `secrets_managed_guard` decides by `current_user` which rows a role may write (the reconciler may
  write only Paperclip's own secrets). A `SECURITY DEFINER` trigger function would always see the owner.
- Decision: such guards are `SECURITY INVOKER`. The `SECURITY DEFINER` functions that must write across the
  guard (`record_work_order_secret`, the key functions) run as the owner and pass. Trigger order matters:
  `secrets_managed_guard` fires before `secrets_managed_path` because PostgreSQL orders triggers by name.
- Consequences: a test asserts the order; a new guard of this kind must be written the same way.

## ADR-011 The orchestration agent, exposure levels and model access live in the schema, with 1.0.1 columns kept in step

- Context: 1.1.0 makes the collaboration agent a required, per-team orchestration agent with a choice of tool, replaces two
  booleans with levels under a team limit, and lets agents narrow models. 1.0.1 services stay in production while
  `-restapi` rolls forward, and the schema may not break them.
- Decision: rules live in constraints and triggers, not in the API alone. A required child (one orchestration agent per
  team) is a deferred constraint trigger, checked at commit, so the team and its agent are created in one transaction.
  Per-surface levels, the team limit and the tool's profile are checked in a `BEFORE` trigger on the changed columns only,
  so an unrelated update does not fail because a limit was lowered later. The 1.0.1 columns (`web_ui_enabled`,
  `rest_api_enabled`, `may_expose_collaboration`, `agents.model_id`) are kept in step by triggers and removed in 2.0.0.
  Guards that depend on `current_user` are `SECURITY INVOKER` and separate from the `SECURITY DEFINER` guards that read
  other tables (ADR-010); trigger names that must run first sort first (`team_collaboration_a_levels_sync`).
- Consequences: the down migration is lossy for data that 1.0.1 cannot hold (Buzz rows, model selections, inference
  profile rows) and says so in its header; foreign keys to `team_models` are re-added and validated only when the data
  allows it.
